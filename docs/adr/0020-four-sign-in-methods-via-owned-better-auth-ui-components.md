# Sign-in gains four methods via owned, editable better-auth-ui components

_Decided 2026-07-28. See tracking spec [#125](https://github.com/soorya-u/cyrus/issues/125)._

The only way into Cyrus was a single "Sign in with GitHub" button that immediately triggered the GitHub OAuth redirect. This blocked anyone without a GitHub account, and — more acutely — it blocked agentic/automated testing entirely: with the Playwright cross-peer E2E harness removed ([0019](./0019-remove-end-to-end-test-suite.md)), the only remaining way to drive the app end-to-end is `playwright-cli` against a running dev server, and there was no form-fillable credential path an agent could submit through. A dedicated `/auth` page now offers four methods — GitHub (unchanged), Google OAuth, Magic Link, and Email+Password — with every existing entry point (the homepage hero CTA, the `/auth/device` device-authorization flow) routed through it via `callbackUrl` instead of jumping straight into GitHub OAuth.

Magic Link is configured with `disableSignUp: false`: a first-time email auto-creates the account and signs the user in, matching how GitHub/Google already auto-provision on first login. Treating magic link as a standalone, equal-parity sign-in method (not a secondary path gated behind a pre-existing account) was a deliberate correction — the default `disableSignUp: true` would silently break first-time sign-in for anyone without a prior account, which contradicts presenting it as one of four equal options.

Email+Password stays dev-only, gated server-side on `NODE_ENV !== "production"` (already implemented and integration-tested before this ADR) and additionally hidden client-side behind a `VITE_IS_DEV_MODE` build flag so it never renders in a production bundle. Its sole purpose is unblocking `playwright-cli`-driven agentic sign-in against a local dev server — it is not a real user-facing auth method and there is no corresponding sign-up UI; dev/test accounts are provisioned directly against the API, the same way the existing integration test already does.

The sign-in form, linked-accounts panel, and active-sessions panel are adopted from `better-auth-ui`'s shadcn-style component registry (`bunx shadcn add <registry-url>`) as owned, editable source copied into this repo — not consumed as an opaque library, and not the full dynamic `<Auth/>` catch-all router (which would also expose sign-up/forgot-password/verify-email views this app doesn't offer). Only the standalone `<SignIn/>` form is used, with its "forgot password" and "create an account" affordances removed directly in the copied source, and its OAuth buttons rewired to the existing `ProviderButton` component (preserving its desktop-specific navigation handling) rather than whatever provider-button variant the registry would otherwise pull in. This keeps the app in control of its own auth surface instead of depending on upstream's product decisions.

The magic-link email is rendered and sent from `apps/server` directly: `MagicLinkEmail` is imported from `@better-auth-ui/react`'s `/email` subpath and invoked via `React.createElement` (not JSX syntax), piped through `@react-email/render`, and dispatched via the `resend` SDK. Avoiding JSX syntax means no `jsx` compiler option, no shadcn tooling, and no shared package are needed in `apps/server` — it stays a plain Hono/Workers backend with one small render-only React dependency, rather than growing a parallel frontend toolchain or a new cross-package boundary just to send one templated email.

No new automated end-to-end suite is introduced for any of this. Per [0019](./0019-remove-end-to-end-test-suite.md), `playwright-cli` against a running dev server remains the manual way to exercise these flows end-to-end — the dev-only Email+Password method exists specifically to make that workable, not to reintroduce Playwright into CI.
